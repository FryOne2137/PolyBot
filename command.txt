# 4a. Izolowany test jakości filtra z etapu 1. Obie strony używają dokładnie

# 8 losowych + obowiązkowe ruchy taktyczne, a model B pełny policy prior.
# Wynik A bliski 0.50 oznacza brak istotnej utraty jakości; <0.45 sugeruje

# 5. Liga z curriculum. Pierwszy model może korzystać z teachera oraz objectives:
# krótkich, wielokrokowych rolloutów, które przekazują sygnał wioski/miasta do
# ruchów prowadzących do celu. Po pierwszym awansie teacher i actor-critic są
# pomijane, ale działa mały refresh objectives; champion dostaje 65% gier, a
# populacja trenuje 6000-12000 kroków przeciw championowi i historii.
# Początkowo o awansie decyduje wyłącznie płaska polityka. Dopiero po realnym
# płaskim awansie wykonywane jest 10 sparowanych gier przy 32 symulacjach;
# search@32 musi ściśle pobić raw policy na tych samych mapach.
# Dwa kolejne udane probe'y zapisują status MCTS-ready. Od następnej rundy MCTS
# staje się dodatkową bramką awansu; nieudany probe zachowuje starego championa
# i zapisuje płaskiego kandydata jako challengera. Dlatego komenda ma co najmniej
# 3 rundy: dwie mogą potwierdzić gotowość, a trzecia już użyć nowej bramki.
# Bramka populacji priorytetowo traktuje wynik gry; przejęcia i completion są
# tie-breakerami, a historyczny floor pozostaje twardym zabezpieczeniem. Ciężka
# drabina MCTS jest wyłączona przez --population-games 0.
# Checkpointy
# po promocji trafią
# do models\league\, pełna historia do models\league\league.sqlite3, a wykresy
# do runs\league\train\round_001, round_002 itd.
# Stały --seed jest bazą wielu map, nie jednej mapy. Każda runda ma odległy
# seed self-play, a bramka osobny, nieużywany w treningu zestaw map. Aktualny
# run wznawia champion-002 i tę samą SQLite, aby kod rozpoznał etap
# champion-population. Po kolejnym awansie podmień tylko --champion-in na
# najnowszy champion-XXX.pt. Jeżeli nie było promocji, ale
# log podał "challenger retained", zachowaj tego samego --champion-in i dopisz
# --challenger-in models\league\champion-challenger-XXX.pt.
